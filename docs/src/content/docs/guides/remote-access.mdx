The terminal chat is one way in. The other is the **server**: one command turns a workspace into
something your phone can talk to over your own network.

```bash
nocturn serve            # listens on :8080 by default, or $NOCTURN_ADDR
```

The server is not a cloud service and does not phone home. It listens on your LAN, announces itself
over Bonjour/DNS-SD as `_nocturn._tcp` so the companion app can find it without you typing an IP,
and speaks a small tagged-JSON protocol over one WebSocket per device.

## Pairing a device

Every connection is gated on a bearer token, and the server never stores the token itself — only its
SHA-256 hash, compared in constant time. Getting a device its token happens in one of three ways.

**The first device** redeems a bootstrap code that the server prints at startup (`POST /pair`). That
is the only time a code comes from the machine itself.

**Every device after that** asks an already-paired one for permission:

1. the new device posts a join request (`POST /join`) and gets back a `joinId` — never a code;
2. the request appears **live** on every connected paired device, which is the only place the code
   is ever shown;
3. you read the code on the trusted device and enter it on the new one (`POST /join/confirm`), which
   redeems it for that device's own bearer.

The property that buys: a device that is merely on your network cannot join. It needs a human at an
already-trusted device to hand it a code.

**A device that cannot read a code** is enrolled *for* — a speaker in a hallway has no display to
show one and no keyboard to enter one, so the exchange above has nothing to work with. An
already-paired device asks the server to mint a bearer on its behalf (`POST /devices`) and hands it
over. Letting such a device enrol itself is not the alternative: anything that can enrol itself is
not being authorised by anyone.

## What a device is, and what that lets it do

Every device carries a **class**, which is a fact about the device rather than a list of permissions.
What a class may do is decided in one place, so the rules can change without rewriting what is
already stored.

| Class | May answer approvals | May enrol devices |
|---|---|---|
| `app` | yes | yes |
| `appliance` | no | no |

An **appliance** is anything with no authenticated input path — a voice satellite, a doorbell, a car.
Whoever is present can operate it and none of them identified themselves, so nothing it reports is
anybody's consent. It is not shown approvals at all: a connection that may not answer one is never
attached to the approval broker, so there is nothing for it to answer *with*.

Enrolment follows one rule rather than a list of exceptions: **a device may only enrol a class whose
abilities its own class already covers.** An appliance therefore enrols nothing, so a stolen
appliance token cannot multiply into a household of equally trusted microphones.

## What the app can do

The companion app talks to the same workspace the terminal does — same conversations, same agents,
same grants. The protocol is one tagged message per action (`chat.submit`, `chat.open`,
`agent.fire`, `approval.resolve`, `reminder.list`, …), and everything the assistant produces streams
back the same way (`chat.token`, `chat.thinking`, `chat.tool`, `approval.request`).

Two consequences worth knowing:

- **Conversations are not per device.** Start something in the terminal, pick it up on your phone.
- **The first answer wins.** If two devices are shown an approval, whichever answers first resolves
  it; the other is told it was resolved. This is also why an appliance is never shown one — it would
  outrace the phone it exists to defer to.

## Approvals when nobody is looking

This is the reason the server exists. An agent running on a schedule hits something that needs your
yes, with no terminal in front of it. If a device is paired, the ask is routed out of band: a push
wakes your phone, you approve or deny in the app, and the agent continues or stops.

The push carries **no authority**. It is a wake signal and nothing else — the decision travels back
over the authenticated WebSocket, never in the notification. A notification that arrives twice, or
gets replayed, cannot approve anything.

With no paired device, an agent set to `guarded` behaves as `strict`: the ask is denied and the run
reports why. Missing setup reduces authority; it never grants it. See
[Approvals](/nocturn/guides/approvals/).

### Setting up push today

Waking a phone that is not on your network needs Apple's notification service, and today that means
**your own** Apple Developer account: a `.p8` signing key, its key id, your team id and the app's
bundle id, set as the four `NOCTURN_APNS_*` variables. Nothing else changes — with the variables
unset, approvals still reach every attached device over the LAN. You simply do not get woken while
the app is closed.

That is a real barrier, and it is the wrong one for a tool meant to be downloaded and run.

**A hosted relay** <Badge text="Planned" variant="caution" /> will remove it: a small public service
that holds the APNs credential so you do not have to, and forwards a wake to your device. It stays
consistent with everything else here only because of what a push already is — a signal with **no
authority**, carrying no decision and no content. A relay therefore learns that some device should
look at its server, and nothing about what is being asked or how you answered. The decision still
travels over the authenticated WebSocket, directly between your server and your phone, and a relay
that went hostile could annoy you but never approve anything.

## Not there yet

**Android** <Badge text="Planned" variant="caution" /> — the companion app is iOS today. The app is
Angular under Capacitor precisely so that the second platform is a build target rather than a
rewrite; what genuinely differs is the push transport, since Firebase Cloud Messaging replaces APNs.

**Messaging channels** <Badge text="Planned" variant="caution" /> — starting and steering a
workspace through WhatsApp or Telegram, with approvals in the same conversation.

**A public HTTP API** <Badge text="Planned" variant="caution" /> — the WebSocket protocol is
internal to the app today; a documented, stable surface for your own tools is not something to build
against yet.
